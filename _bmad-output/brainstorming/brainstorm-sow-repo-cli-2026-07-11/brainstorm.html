处方两剂

发布是事务 教练 账 L14

上传、索引、purge、验证是一个原子动作：任何一环失败，整体报错。从此世界上不再存在"忘了某步"。

sow add 单命令入库 教练 账 L15

自动识别 deb/rpm，推断目标仓库、OS 与架构，Go 原生签名建索引。容器与 stash 仪式，就地消灭。

"少问引导性问题，直接给靠谱的技术分析。"

Vonng · 调频 核心诉求就一句话——发布管理原子事务化：同步开销最小化、元数据 verification 完善、一个 CLI 管到底（同步 / 加包 / 减包 / 校验 / 再同步）。 账 L16

状态模型 教练 账 L17

每个仓库一份 manifest（path, size, sha256），本地 / 远端 / CDN 三层状态对账——一份 diff，既驱动最小同步，也驱动校验。

原子性核心 教练 账 L18

内容寻址 + 单点翻转：apt 用 by-hash 布局（reprepro 不支持，Go 原生可以），yum 的 repodata 天然 hash 命名。先传包体与 hash 元数据，最后翻转单文件。

purge 最小集 教练 账 L20

内容寻址后只需 purge 翻转点文件，不用 Purge Everything；就算漏了，旧索引依然自洽——它引用的旧文件都还在。

定源
印一 · 真相源拍板 账 L21
本地开发机目录是真正的真相源；对象存储是权威交付副本，但只是它的滞后快照。不能靠反复扫远端对账——耗时，且 API 调用是真金白银。

这一章拍下去，整个状态模型有了原点。随后教练顺势补上两件配套——

远端跟踪清单 教练 账 L22

git 模式：每次 publish 后本地记下"已推送 manifest"（类 refs/remotes）。下次 diff = 本地树 vs 跟踪清单，零远端 API 调用；rclone 用 --files-from 只传差异文件。

远端检查点对象 教练 账 L23

bucket 里存一份 .sow/manifest.json 加代际号：1 次 GET 即可发现漂移（别人动过 bucket、上次发布中断）；CAS 写入兼做发布锁。全量 ListObjects 深审计，留给 sow fsck。

技法 02 · ASSUMPTION REVERSAL · 假设反转

五连翻

十几条"理所当然"被逐一按在桌上翻面：有的当场作废，有的翻出了更好的形状。翻到第五张时，逼出了全场最漂亮的一次反击。

两式
印二 · 两类操作 账 L25
两类操作要分开伺候：① 增量更新 = stash → commit，只检查变化的部分，像 git add；② 大检查 = 对某个目录做完整的 rsync 式对账，确保本地完整映射到云端。

一条便宜的日常路径，一条昂贵的审计路径——这个分野在后面的快照物化与 CDN 策略里还会一再回响。

manifest 进 git Vonng 账 L26

建一个专门的 git 仓库存清单文件：一行一条文本记录（变更前后大小 / 校验和，类 diff 格式），用 diff 数据做增量提交，全部变更历史可追溯。

教练具体化 教练 账 L31

每仓库一个当前态 manifest（排序、一行一文件），git diff 天然就是变更记录；每个发布目标（cf / cos）各持一个"已发布 ref"，两朵云允许各自滞后。

收编

教练 .sow/（manifest 与缓存）与 .pool/（CAS 池）作遮蔽目录；oss/ 与 pro/ 两棵 hardlink 物化树，就是各自 bucket 的 1:1 镜像——Nginx 指树根即可托管。 账 L46

追问

Vonng APT 已有 pool 加前缀拆分，YUM 能不能也搞包池？YUM 目录巨平巨乱；Pro 是全新仓库，想借机改布局。 账 L38

查证

教练 primary.xml 的 location href 是 baseurl 相对路径、可含子目录——Fedora / EPEL 就是 Packages/<首字母>/ 布局，标准做法、全客户端兼容；跨仓库 ../ 共享属非标准，有兼容风险，不上线。 账 L42

卷宗 · 第五翻的三个回合
回合一

Vonng 先抛三问：①"本地树 = 最终形态"约束下 snapshot 怎么实现；②本地能 hardlink，对象存储上的重复上传怎么办；③腾讯 CDN / Cloudflare 有没有类硬链接的省空间机制。 账 L45

回合二

教练 APT：单 archive 根 + 共享 pool，快照即套件（dists/jammy-20260701），aptly 同款模型、完全标准；YUM：每快照独立 repo 树，bucket 上未变的包用 server-side CopyObject 晋升——传输层的"硬链接"。但明确结论：R2 / COS / 两家 CDN 都无内容去重语义，server-copy 省的是流量，不是存储。 账 L47–L49

于是教练给出方案 A / 方案 B（见上）。用户看完，只回了一句——

诘问
印四 · "太蠢"之问 账 L51
stable 指针若靠整树 server-copy，等于把已有历史再全拷一遍——太蠢。apt / yum 有没有原生的指针 / 别名机制？

好问题比好答案值钱。教练回去翻了几十年的发行版基建，带回了两个一直就在那里的答案——

APT 原生指针：dists 别名 教练 账 L52

dists/jammy 别名 = 一套几 MB 的小索引（Suite 字段对齐、重签即可），pool 完全共享——Debian 官方 archive 的 dists/stable → trixie 就是同款模式。从不存在 50GB 的拷贝。

YUM 原生指针：mirrorlist 教练 账 L53

mirrorlist / metalink 间接层（CentOS / Fedora 用了几十年）：.repo 写 mirrorlist=…stable.txt，该文件一行指向当前快照 baseurl。通道翻转 = 改一个小文件 + purge 它。零拷贝，零边缘魔法。

指针方案定案 账 L55 · L56

APT 用 dists 别名（小索引 + Suite 字段重签），YUM 用 mirrorlist 原生间接层；包体永不重复拷贝。Pro 的 token-in-path 与静态 mirrorlist 有冲突——由已有的鉴权 Worker 动态模板化 mirrorlist，回填请求里的 token；OSS 纯静态无此问题。

快照经济学 账 L54 · L57

快照本质 = manifest 的一个 git ref，bucket 里物化几份只是发布策略参数：只物化 stable + 最近 N 个月，更老的快照按需从池 + 清单重建——历史全保，存储封顶。

本环节顺手过账
L29上游同步（reposync 替代）：先调研现成开源方案；aptly 与 reprepro 的布局差异，立专项调研。

元数据三层定案 账 L39
正典git 里的排序 TSV manifest——纯文本，用户直觉正确。
派生SQLite 只读缓存——随时可重建，gitignore，供依赖闭包等查询。

合一仓库

风暴的最高点不在任何技法脚本里——是台账上标着"重磅"的一行。此前所有铺垫（包池、视图、指针）在这里合拢。

合一
印五 · 重磅 账 L65
Pro 与 OSS 合二为一——一个物理仓库，靠元数据控制访问：token 前缀保护企业元数据；OSS 只用 latest、无 debug 包生成"精选集"元数据公开暴露。一仓两视图。

开题时还是"双通道同步导出"的老大难，收笔时整个问题不复存在。

教练判定：成立，有边界 教练 账 L66

对开放内容（历史版本 / debuginfo / 快照索引）成立——Pro 卖的是策展与服务（快照、钉版、SLA），不是比特机密，元数据即产品。但未来若有闭源 Pro 专属包，必须放进真 token 门控前缀——不能靠"索引里不写"的隐匿式安全。

分池原则修正 教练 账 L67

按机密性分池（public 池 / gated 池），不按商业通道分桶。OSS / Pro 只是元数据命名空间；apt / yum 元数据全用相对 href，token 前缀天然全程携带；鉴权 Worker 把 token 路径统一映射到两类池。
