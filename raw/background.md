# sow 项目设计目标。

一个 Go 编写的仓库管理命令行工具。
用于管理 Pigsty 软件仓库，同时处理各种管理职能。


这里有一些背景我想跟你交代一下，作为咱们讨论的基础。
就是说，我们这里有一个仓库，叫 Pigsty repo。

~/pgsty/repo

APT 仓库和 DNF 仓库同时还要负责从上游的 pgdog 仓库往下游同步，另外还有几个具有很复杂功能的构建仓库。
这个被管理的仓库目前位于这个位置，你可以先扫描、研究一下。里面有很多 Makefile，也就是我们日常要执行的这些命令。




总的来说，我认为有几个大功能是要有的。

首先，我们目前有一个 APT 仓库和一个 YUM 仓库。它们的管理方式如下：
1. APT 仓库：目前由 reprepro 程序负责管理。
2. YUM 仓库：目前是在容器中通过 createrepo_c 来管理，有时还会用到 repo2md 或 modulemd-tools 等工具。

我们目前的构建和支持规划：
• 目标系统：需要构建 EL 7、8、9、10（主要是 8、9、10）的 YUM 仓库，以及 Ubuntu 20 到 26、Debian 11 到 13 的 APT 仓库（不过目前活跃的操作系统比这少一些）。
• 架构支持：目前支持 AMD64 和 ARM64 两种架构，以后可能会有更多。
• 规模：总共涉及 16 个操作系统，每个操作系统下都有很多包，并对应一系列仓库。

不同仓库的作用和同步策略不一样：
• Infra 仓库（Pigsty Infra）：是一个架构相关、但大版本无关的仓库。它只区分架构（AMD64/ARM64），不怎么区分操作系统大版本。这种通常放 Go 编写的二进制项目，只要架构相同，在任何系统上都能跑。
• pgsql 仓库：存放与具体操作系统大版本紧密链接的包（比如数据库相关的包）。
• PGDG 仓库（PostgreSQL 官方仓库）：从 PostgreSQL 官方开发组的上游源同步下来的一个子集。为了优化，我们只同步 Pigsty 用到的操作系统包，这是一个关键点。
• Percona 仓库：同样是从上游同步下来的。

关于从上游同步（PGDG 和 Percona）的策略：
目前的策略是只保留最新的版本。但我希望新的工具能够支持更灵活的策略。

比如说，我会有一个普通仓库和生产仓库，相当于两个 channel。后续我可能会复制一份仓库：

1. 生产仓库：保留全量的历史包和 debug 信息包，保留所有的历史。
2. 开源仓库：滚动更新最新的版本。

这是两个不同的策略，需要你来管理。

另外，我们还需要设计支持以下几个功能：

1. 跨平台的包管理
   既然我们已经有了 Go 二进制，是不是可以直接在里面实现 APT 仓库管理和 YUM 仓库管理？我知道应该有相关的开源库可以做到。这样我们直接就可以取代 dpkg 和 createrepo-c，在 Go 里面原生实现跨平台的包管理。

2. 离线仓库同步
   像 PGDG 这种上游把 rsync 同步关掉的仓库，APT 还好，有 apt-select 或 apt-mirror 可以去同步；但 YUM 仓库就比较麻烦了，虽然可以用 reposync 一个一个仓库去同步，但确实挺麻烦的。
   之前我们是在 Docker 容器里去同步，这次我希望尽可能有一个 OS 原生的解决方案，也就是在 Go 里面原生解决，不要依赖容器。但如果你评估后觉得实在没有办法，或者用容器确实太方便、太简单了，那我也接受你时不时调用几个特定的容器。不过只要有可能，我们还是尽可能用原生的 Go 来实现。

概括一下这几个需求。我们要做一个包管理工具，需要解决以下几个核心问题，我们来头脑风暴对一下方案：

1. 仓库管理基础功能：
   • 支持仓库管理，能够方便地向仓库中添加包、从仓库中移除包，以及列出仓库中的包
   • 支持脚本管理

2. 同步与导出机制（OSS 仓库与 Pro 仓库）：
   • OSS 仓库（开源仓库）只保留最新版本的包，Pro 仓库保留所有历史版本的包
   • 建立双向同步机制：
   (a) 追加同步：当开源仓库做得差不多了，能把开源仓库里最新的包追加到历史仓库（Pro 仓库）中
   (b) 裁剪导出：能随时从历史仓库中，只提取所有包的最新版本，导出生成一份新的开源仓库

3. 多域名与上游配置：
   每个仓库（OSS 仓库和 Pro 仓库）都需要对应国内和国外两套域名：
   • 国外上游域名：repo.pigsty.io 和 pro.pigsty.io（基于 Cloudflare）
   • 国内上游域名：repo.pigsty.cc 和 pro.pigsty.cc

4. 上传与同步管理（微妙且复杂）：
   • 引入 Rclone：目前 Makefile 里是用 Rclone 来管理对象存储（COS）的。因为 Rclone 是用 Go 写的，我们可以考虑直接把它的代码抠下来，作为 Library 嵌入到我们的工具中，实现本地内容到云端的同步
   • 增量上传与差异对比（Diff）：由于文件数量较多，需要支持 Diff 功能，每次只上传或更新发生变化的文件，以减少云端 CDN 和对象存储 API 的调用次数
   • 变更日志：每次更新变化了哪些文件，都需要有地方记录详细的日志
   • 缓存失效机制：结合腾讯云 API 和 Cloudflare API，当文件同步上去并完成发布后，需要自动调用 API 使对应的 CDN 缓存失效

你可以看一下我们之前的文档设计，扫描一下仓库里的 Makefile 和布局结构。思考一下，如果我们要实现这样一个包管理工具，需要解决哪些技术问题？应该怎么去设计这个方案？

这里我觉得有两类操作：

1. 增量更新：我们每次看仓库出现了哪些变化，相当于先 stash，最后 commit 的时候就提交到仓库。通常来说，我们只需要增量检查变化的部分就可以。这就类似于 git add（或者说 so add）把包加到里面的逻辑。
2. 大检查：有时候我们会想进行一次完整的大检查，比如直接针对 apt-pgsql、apt-deb 的逻辑。这种情况下，需要完整地针对某一个目录去跑一个 rsync，确保本地完整地映射到云端。

我觉得这是两个不同的逻辑，你应该去补充一下。

我觉得我们可以创建一个 Git 仓库，专门在里面记录一个 manifest 清单文件。

这个清单文件用来记录哪些文件出现了变更，以及变更前后的信息（比如文件大小、校验和等），采用一行一条的文本记录形式，类似于 diff。

然后，我们利用这个 diff 数据去做增量提交。这样一来，所有的变更历史现在就都可以追溯了。


那么我们进入第二个技法：假设反转。在这个部分，我跟你讨论一下那些看似理所当然的事情。

问题一：APT 仓库必须依靠 reprepro 吗？

我觉得不是。但我们要评估复杂度：如果我们在 Go 语言里有这种开源的库，能起到 reprepro 的作用，那就可以。我并不要求服务端仓库一定得长什么样，大体上只要客户端接口不发生变化，依然能下载安装这些包就行，你服务端怎么折腾我是不管的。

所以这种情况下，只要把条件一放宽，我觉得在 Go 生态里处理 APT、RPM、YUM 的这种包应该是有，而且应该不少。只要这个成立，我们就可以这么做，而且我们优先就这么做。


关于签名这个事情，我们可以假设本地已经有了 GPG key，这个密钥我甚至可以直接在环境变量里告诉你。

之前我们的做法是把密钥明文拷进 Docker 镜像里，但我觉得咱们这个工具应该优先做成能在本地（比如 Linux、macOS）直接运行。

对于 GPG 签名，你可以假设系统原生自带 GPG client，或者你直接用某个 GPG 库去读取。

我的建议是：如果需要 passphrase，你最好能支持从环境变量或者命令行参数中读取。


RippleSync 这个问题我觉得可能会棘手一点，但其实也还行。

关于分包（aptly 与 reprepro）和存储选型的几点想法，给你回复一下：

1. 关于分叉的拍板：
   我目前不清楚 aptly 的底层布局跟 reprepro 有什么具体区别，这肯定需要专门启动一个调研任务去研究。不过我觉得只要找一个库进行自研，能保持一致就行。

2. 关于 Rclone（阿克隆）：
   我们只需要保证都是 S3 兼容接口即可。Cloudflare 和腾讯云 COS 都是标准的 S3 接口，所以问题不大。

   但这里面有几个 API 需要你研究一下，特别是缓存过期的 API。你评估一下是直接使用 Cloudflare 和腾讯云的 SDK 会不会更简单？

   因为我们这个项目是一个内部使用的工具，并不需要考虑太强的通用性。既然现在选型了 Cloudflare 和腾讯云 CDN，那直接用它们各自的 SDK 也无可厚非，并不是非得用统一的 S3 SDK。





关于仓库元数据管理、包管理工具以及签名机制，我有以下几点想法：

1. 元数据存储选型
   关于元数据的存储，你可以考虑使用 SQLite，或者直接用 PostgreSQL（PG）。
   虽然复用 Postgres 会引入一个依赖，但考虑到我们已经有 PG 在存储很多扩展的元数据了，我并不介意继续复用它，我觉得影响并不大。
   当然，如果你需要计算包依赖等，我希望尽可能还是优先用本地的 SQLite、文件或者 PG。你自己来做技术选型，我个人觉得纯文本可能就够用了，用起来也会更简单。

2. 包管理工具实现
   • APT：既然有现成的工具，咱们就直接用现成的。
   • Yum：如果没有现成的，我们就自己来实现。

3. 签名与仓库模式
   关于签名，我的看法是我们可以用自己的签名进行重签。
   因为最理想的情况是“一个仓库走天下”，所有供应链的安全与分发职责都由我们自己负责。所以，我们不一定非要采用 Verbatim（原样引入）模式。
   还有一个原因：比如上游的 PGDG APT 仓库，它通常只保留最新版本。如果我们的策略是要保留所有历史版本，直接同步就会遇到一个严峻的问题。因此，我认为我们可能需要采用自己 rebuild 的模式。

4. 对，我们就直接用这两家的 SDK 好了。因为我们说明白了，这个是专用软件，不要过度设计，好吧。

关于包池（pool）这个模式，我不太了解，但我想跟你探讨一下。这次我们做 Pro 仓库是一个全新的仓库，我希望能利用这个机会做一些改动：

1. APT 我们现在用的是包池结构，但 YUM 这里我不知道能不能弄包池。
2. 还有一个问题：APT 那里实现了自动做前缀拆分，所以每个目录都不会有太多包；但是 YUM 这边，它就弄得非常复杂。

我不太清楚 YUM 能不能这么搞，但你这个思路我认为值得探索研究一下。




我对于布局是这么想的：因为我们这个仓库除了要放在对象存储之外，有时候也要在 Nginx 里面作为一个普通的目录对外提供服务。所以从目录结构上来看，这个目录本身应该就是该仓库的最终形态。有一些文件可以遮蔽，但里面一定要有一个目录，整个要完整对应着对象存储上的树。

虽然我不太确定这是不是正确的做法，也是需要商榷的问题，但我确实有这个硬性需求。因为在本地 Nginx 上跑（即我把这个目录整个复制到 Nginx 上）能让该仓库直接托管，这对于我拉起一个镜像站点来说非常重要。所以，本地目录跟对象存储需要保持持续一致，这是大前提。

如果是这样的话，我突然想到了一个思路，不知道可不可行。

我们现在的仓库等于是一个当下最新版本包的快照。那我是不是可以把所谓的 Pro 和 OSS 仓库合二为一？也就是说，通过控制元数据的方式来控制仓库的访问。

具体的设想是：

2. 与此同时，开源版仓库只用最新的包（不包含 debug 包）来创建元数据，相当于一个“精选集”。
3. 我们只把这个精选集的元数据对开源版的客户暴露。
