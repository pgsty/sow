topic: repository-scoped single-payload layout
purpose: canonical forward contract for implementation and validation
updated: 2026-08-05T17:54

- (direction by user) Only one package payload copy is required within one Repository and one publish prefix; cross-Repository and cross-prefix deduplication is explicitly out of scope.
- (constraint by user) The canonical Repository root contains pool and dists directly; no release or reposync top-level directory may be introduced.
- (decision by user) Object-storage publication must not materialize package hardlink aliases as duplicate object keys; package hardlinks are not a correctness invariant.
- (decision by user) Default EL reposync compatibility may be dropped rather than sacrificing the single-payload object-storage invariant and direct pool plus dists layout.
- (capability) CAP-1 one canonical package payload path per package within each Repository and publish prefix.
- (capability) CAP-2 protocol-native APT and ordinary DNF clients consume one root pool through archive-root and computed parent-relative metadata references.
- (capability) CAP-3 pool and dists form the exact relocatable static publication unit for filesystem, HTTP, and object-key-equals-path targets.
- (capability) CAP-4 generations, snapshots, and GC retain metadata plus repository-wide payload references without per-view or per-snapshot payload aliases.
- (capability) CAP-5 explicit standalone compatibility export defaults to copy and may use controlled local hardlinks only by opt-in outside the canonical Repository.
- (decision) The approved single-payload layout is now paired with explicit repository identity, target publication, by-hash/pointer ordering, evidence-fenced deletion, export, and migration contracts; all remain unimplemented until next acceptance evidence passes.
- (decision by user) Accepted deduplication boundary: one physical package payload per Repository and per publish prefix; cross-Repository/target-prefix deduplication is out of scope. Align every forward design and reference to this boundary.
- (decision by architect) Canonical public tree remains exactly <workspace>/<repo>/{pool,dists}; APT uses exact archive-root Pool paths, RPM uses computed parent-relative hrefs, canonical per-view package aliases are forbidden, and default EL reposync is unsupported. Standalone compatibility is an external sow-rpm-leaf-v1 export, copy by default and hardlink only as an explicit trusted read-only optimization.
- (decision by architect) Direct object publication is single-writer and uses exclusive storage write authority without a target-global owner registry. Targets without atomic conditional delete retain and report unreachable keys; Cloudflare R2 validates publish plus delete-disabled behavior, and legacy C2 migration to R2 uses a new empty prefix.
- (decision by architect) Frozen interoperability details: APT Filename is the exact canonical path and URI encoding happens once at retrieval; retained generations use exact metadata plus refsets; export marker/manifest exclude self-hash cycles and v1 has no in-place replace; C2 commit-intent makes all later recovery forward-only.
- (decision by reviewer) Final wire closure: GenerationID is a fixed 20-digit JSON string, sizes use canonical ASCII decimal spelling, migration receipts freeze exact bytes and boundary goldens, and declarative Changeset order is distinct from target publication order.
- (decision by reviewer) Export signer closure: marker copies the bound Built Generation RPM-view signer_identity byte-for-byte; source-bound verification compares that record and key, standalone verification uses an external trusted identity-to-key map, never an unfrozen policy/key concatenation. Size bounds, overlap cases, plan replay, strict nested JSON, and export crash/mismatch vectors are acceptance requirements.
- (implementation status) Current 0.3 source implements the single-payload renderer/checker, v0.2 forward migration, retained wire, local GC, external RPM leaf export, and target-scoped filesystem/R2 publication. Local unit/fault/mock evidence is distinct from still-unverified live client, completed-export reposync, proxy, and real R2 release gates.
